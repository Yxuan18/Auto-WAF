# 46 个测试全绿，生成的 WAF 规则是错的

> 3386 个突变体只杀死 900。全绿证明测试跑过，变异测试证明测试能抓住。

Auto-WAF 做的事一句话能说清：喂它一个 PoC 报文，它吐出 ModSecurity 和 Suricata 规则。为了让这条流水线可信，我给它配了 46 个测试，一直全绿。

然后我在补杀突变体之前的代码上（a0b215c）做了个实验。`generators/suricata.py` 的 `_find_param_location` 里有这么一行：

```python
poc_info.get("query_params", {})
```

把键名换成 `None`，`get` 落进默认值，query 参数字典变空。一行代码，一个词。

喂进去一个纯 query 的 SQLi PoC：`GET /search?q=1 UNION SELECT username, password FROM users--`，参数选 `q`。改动前后，两次生成的规则 pcre 部分分别是：

```
pcre:"/q=(?i:\b(select|union|update|order|insert|\x2f\x2a\x2a|delete|updatexml|...
```

```
pcre:"/q=[^\x0a\x0d\x26]+/i"
```

跑测试。46 个，全绿，一个不红。

先看死掉的是什么。参数名 `q` 还留在规则里，`q=` 一个字符不少。死的是参数值与参数位置的识别——`q=` 后面那串 SQL 注入特征，`select`、`union`、注释符，塌缩成一个通配符 `[^\x0a\x0d\x26]+`：除了换行符和 `&`，匹配任何内容。规则还在告警，`sid` 还在编号，看起来还在干活，攻击特异性没了。一条认得出注入 payload 的规则，变成一条对任何非空参数值都会命中的规则。

这比参数名消失更吓人。参数名丢了，规则文本上一眼扫得出来；特异性丢了，规则结构合法、转义规范、测试通过，只有拿真的 payload 打过去，才知道它已经不设防。

46 个测试在测什么？翻开当时的断言：`startswith("alert http")`，规则里有 `sid:`。接线断言。它们验证流水线产出了一个长得像规则的东西，从头到尾没验证过规则的内容对不对。全绿在这个体系里的含义，比字面上窄得多：测试跑过了，没崩，断言的字段都在。一张施工验收单，验收的是管道通了，水质一栏空着。

变异数据是 mutmut 给的。它做的事很机械：把常量翻一下，比较运算符换个方向，字符串改一个字符，每个改动生成一个突变体，跑一遍全部测试。测试变红，突变体算杀死；测试照绿，存活。首跑的数字记录在 `.claude/tdd-guardian/plan-2026-10-07-mutation-kill.md`（2026-10-07）：突变体 3386，杀死 900（26.6%），存活 1759，无测试覆盖 727。接近四分之三的机械改动，测试毫无反应——其中约两成，测试从未执行到。

900 这个数字把全绿重新标定了一遍。全绿说明测试跑过；变异测试量出来的是另一件事：这套断言对机械改动的无感面有多大。26.6%，无感面占七成多。

四轮补杀，杀到 36.3%，顺手修了四个真缺陷（commit 556dd70）。把四轮暴露的问题归拢，前三类是测试写得不够，第四类换了一个方向，是测试管不了的事故。

第一类，断言语义不够。修的第一个真缺陷在 pcre 转义上：`_build_uri_pcre` 用 f-string 拼 pcre，`\b` 写一次，落进规则文本的是退格符——词边界从来没存在过。接线断言查前缀、查 `sid`，退格符躺在 pcre 里，测试全绿。变异测试把存活者指到这几个函数，补写内容级断言的当天，这个缺陷当场现形：断言 pcre 里该有词边界结构，真红，修，绿。这个退格符，本身就是顺着变异测试的存活清单摸出来的。

第二类，测试数据域不够。`selected_param=""` 走自动检测路径，而测试数据里从来都是显式给参数名，这条路径没有用例走到。里面藏着一个硬编码的 `vuln_type=""`：自动检测从未真正触发，全绿。info_leak、auth_bypass 两类规则生成函数，171 和 52 个突变体全部无覆盖，原因同款——测试数据里没有这两类 PoC。测试数据的域，圈定了哪些代码永远在暗处。

第三类，指标解读不够。变异得分是三个数——杀死、存活、无覆盖——不是一个百分比。死代码污染分母：`generate_suricata_rule` 的 return 之后躺着 90 行旧实现的残留（Pyright 判定 unreachable），按补杀计划当时的统计，是一百四十多个存活突变体的主要来源。删掉这 90 行，突变体总数从 3386 降到 3296——两个分数的分母不同。反过来，存活也未必是缺陷：`_gen_sid` 里 6 个随机边界突变，语义近似等效，追杀成本大于收益，记为已知缺口，不立项。读分数之前，先把三类数拆开。

第四类，流程事故，测试管不了。更早的一次合并把三个规则生成函数整个误删（a6f2a86 误删，a9534f5 恢复），测试全绿——那三个函数本来就是零覆盖，删掉它们，覆盖率分毫不动。这类事故的防线只能放在产物级：固定一组 PoC，每次改动前后各跑一遍规则生成，比对规则数量与内容的收据，收据变了，门禁拦下。覆盖率这道防线对这类事故是失明的——我一开始把它列进防线，删掉了。

36.3% 这个分数不体面。一个看起来还认真的项目，得分堪堪过三分之一。反论点得先摆齐。

第一条：分数这么低，说明测试本身就烂，先补测试再说。这条我认一半。分数低正是这次复盘的产出——补杀四轮、修掉四个真缺陷之后仍然 36.3%，剩余存活集中在 sec_rules 的字符串细节上（info_leak 一类 112 个），缺口在案，装不了体面。全绿和能抓住之间的距离，本来就该用一个不体面的数字来量。

第二条，最强的一条，长这样：这篇复盘花两千字论证绿测试和错规则同时为真，被当场抓获的缺陷，是 pcre 词边界从未存在；而这个工具的卖点场景，恰恰是 0day 爆发的那几个小时，出一条能挡的规则。在错误代价最高的时刻，部署一套会静默产出坏规则的生成器，制造“已挡住”的错觉，比不挡更危险。这条击中要害，答案只有老实的那个：把“能挡”从形容词变成门禁——生成的规则在部署前，对 PoC 报文本身做一次回放验证，payload 打过去，规则命中，才算数。这一步现在还没做，是下一个工作项。在它落地之前，“几小时内出一条规则”的完整读法是：几小时内出一条通过了回放的规则，快慢看流水线，能挡与否看门禁。

第三条：变异测试贵，每个突变体都要跑全套测试，值得吗。它给的东西至少两样：把全绿的可信度重新标定成一个具体的数字；在补杀过程中直接暴露真缺陷——第一类里那个退格符，就是顺存活清单摸到的。最终仍然要靠内容级断言兜底，回放门禁补上“规则真的挡得住”这一环；真实流量验证目前未做，是已知缺口，记在这里。

四轮之后的终态数字：突变体 3296，杀死 1197，存活 1659，无覆盖 440，得分 36.3%。这个分数摊在提交记录里，复跑的方法写在 README 里：github.com/Yxuan18/Auto-WAF。`_gen_sid` 的 6 个，info_leak 的 112 个，按分布估计都还活着。欢迎来杀几个突变体——杀掉一个算一个，杀不动的，告诉我为什么杀不动。

四轮下来最实的收获是一句换算：全绿证明测试跑过，变异测试证明测试能抓住。区别在心态——把全绿当目标，测试会越写越顺；把能抓住当目标，测试会越写越挑剔。

收尾留一个问题。产物级收据那道门禁还在待办清单上；真实流量验证未做；1659 个存活者的清单随时可以复跑出来。我们的全绿每天告诉我们测试跑过了，变异测试替我们问了另一个问题：这些测试抓得住什么。当生成的规则在真实攻击面前静默失效时，第一个知道的会是谁——用户，攻击者，还是我们自己？
